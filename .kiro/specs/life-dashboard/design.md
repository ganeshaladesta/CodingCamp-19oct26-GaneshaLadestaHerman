# Design Document

## Overview

This document describes the technical design for the Life Dashboard, a single-page personal productivity homepage built with pure HTML5, CSS3, and Vanilla JavaScript (ES6+). The design fulfills the requirements in `requirements.md`. The application runs by opening `index.html` directly in a browser, with no frameworks, no backend, and no build tools, persisting all state in Local Storage.

## Goals

- Deliver a polished, responsive dashboard combining a live clock/greeting, Pomodoro timer, task manager, and quick links.
- Keep the codebase dependency-free and runnable via the `file://` protocol by opening `index.html`.
- Persist all user data in a versioned Local Storage layer that degrades gracefully.
- Maintain accessibility and safe DOM rendering throughout.

## Non-Goals

- No server, database, or network backend.
- No build step, bundler, or transpilation.
- No third-party libraries or frameworks.
- No cross-device sync; data is local to each browser.
- No account or authentication system.

## Architecture

### Execution Model

The application is a single HTML page that loads one stylesheet and one script. Because it must run from `file://`, ES module `import`/`export` is avoided (browsers block module scripts over `file://` due to CORS). Instead, `js/app.js` is a single traditional script organized into clearly separated internal modules using an IIFE namespace pattern. This keeps a single entry point while preserving logical separation.

### Module Organization (inside `js/app.js`)

```
app.js
├── Storage        // versioned load/save, JSON validation, UUID generation, in-memory fallback
├── ThemeController// theme read/apply/toggle/persist, anti-flash init
├── ClockGreeting   // clock interval, greeting selection, editable display name
├── PomodoroTimer   // target-timestamp countdown, circular progress, notifications
├── TaskManager     // CRUD, filters, sorts, search, statistics, rendering, delegation
├── QuickLinksManager// defaults, CRUD, URL validation, new-tab rendering
└── App             // bootstrap: wire modules on DOMContentLoaded
```

Each module exposes a small public API and keeps its own private state. Modules communicate through explicit function calls and a shared `state` object for cross-cutting data (theme, settings), avoiding a global event bus to keep the design simple and debuggable.

## File Structure

```
life-dashboard/
├── index.html        // semantic markup, landmarks, theme no-flash script in <head>
├── css/
│   └── style.css     // CSS variables for themes, layout grid, components, responsive, reduced-motion
├── js/
│   └── app.js        // all modules (IIFE namespace), bootstrap
└── README.md         // overview, features, usage, project structure
```

## Data Models

### Task

```json
{
  "id": "uuid-string",
  "title": "string (trimmed)",
  "completed": false,
  "priority": "low" | "medium" | "high",
  "category": "Personal" | "Work" | "Health" | "Learning" | "Other",
  "createdAt": 1700000000000,
  "updatedAt": 1700000000000,
  "dueDate": "2024-01-15" | null
}
```

- `id`: generated by the Storage UUID helper.
- `title`: stored trimmed; compared case-insensitively for duplicate checks.
- `completed`: boolean, toggled by the user.
- `priority`/`category`: constrained enums validated on input.
- `createdAt`/`updatedAt`: Unix epoch milliseconds via `Date.now()`.
- `dueDate`: ISO `YYYY-MM-DD` string or `null` when unset.

### QuickLink

```json
{
  "id": "uuid-string",
  "title": "string",
  "url": "https://example.com"
}
```

### Settings

```json
{
  "displayName": "string | empty"
}
```

### Theme Value

```
"light" | "dark"
```

## Storage Layer Design

### Versioned Keys

| Key | Value |
|---|---|
| `lifeDashboard.tasks.v1` | JSON array of Task |
| `lifeDashboard.quickLinks.v1` | JSON array of QuickLink |
| `lifeDashboard.theme.v1` | JSON string `"light"` or `"dark"` |
| `lifeDashboard.settings.v1` | JSON Settings object |

### Storage API

- `Storage.load(key, defaultValue)`: reads the key, `JSON.parse`s it; on parse failure or absence returns `defaultValue`.
- `Storage.save(key, value)`: `JSON.stringify`s and writes; wrapped in try/catch to handle quota/availability errors.
- `Storage.generateId()`: returns `crypto.randomUUID()` when available, else a fallback combining `Date.now()`, `Math.random`, and a counter.
- `Storage.isAvailable()`: feature-detects `window.localStorage` with a write/read probe; when unavailable, modules keep in-memory state for the session.

### Error Handling Strategy

- All storage reads are wrapped so malformed JSON never throws into the UI; the module receives its default and continues.
- All storage writes are wrapped so a full or blocked `localStorage` does not crash the app; the in-memory copy stays the source of truth for the session and a non-blocking console warning is logged.
- Defaults are populated lazily: Quick Links defaults are seeded only when the key is absent (not when the user has intentionally cleared the list, distinguished by a sentinel or by treating an explicit empty array as user intent).

## Components and Interfaces

### ClockGreeting

- A `setInterval` updates the time and date display every second.
- On each tick, the greeting is recomputed from the current hour against the Greeting_Hours ranges defined in the glossary (Morning 05:00-11:59, Afternoon 12:00-16:59, Evening 17:00-22:59, Late Night 23:00-04:59).
- The display name is rendered inline with the greeting. An edit affordance (button toggling an inline input) lets the user set the name; on confirm the name is saved to `settings` and the greeting re-renders; on cancel the prior name is restored.
- The interval is cleared on page unload to avoid leaks.

### PomodoroTimer

- **Target timestamp approach**: when Start is pressed, the module records `targetEnd = Date.now() + durationMs`. The display is derived as `remaining = targetEnd - Date.now()` on each one-second tick, eliminating drift during tab inactivity.
- **Pause**: stores `remainingMs = targetEnd - Date.now()` and clears the interval; Start recomputes `targetEnd = Date.now() + remainingMs`.
- **Reset**: cancels any running interval, clears `targetEnd`/`remainingMs`, and restores the full 25:00 display and the full progress ring.
- **Circular progress**: an SVG ring (or conic-gradient fallback) whose stroke-dashoffset is updated to reflect `elapsed / duration`. The ring updates each tick and on theme changes (the ring geometry is theme-independent; only colors come from CSS variables).
- **Completion**: when `remaining <= 0`, the interval stops, the display shows 00:00, and if `Notification.permission === "granted"`, a `new Notification(...)` is shown. The module never requests permission. If not granted, a visible in-app completion indicator is shown instead.
- **Theme continuity**: theme changes only swap CSS variables; the timer module's JS state (`targetEnd`, `remainingMs`) is untouched, so the countdown continues across theme switches.

### TaskManager

- **In-memory list** is the source of truth, mirrored to storage on every mutation.
- **Add**: validates a trimmed, non-empty title and rejects duplicates via a case-insensitive trimmed comparison against existing titles; on success creates a Task with defaults and prepends/appends per the active sort.
- **Inline edit**: an edit affordance swaps the title cell for an input pre-filled with the current value; Enter saves (re-validating against duplicates among other tasks), Escape cancels and restores the original.
- **Toggle/Delete**: event delegation on the list container routes checkbox/change and delete-button clicks to the correct Task by `data-id`.
- **Filters**: All/Active/Completed/Today applied as predicate functions over the list; "Today" includes tasks due today plus overdue incomplete tasks.
- **Sorts**: manual (preserve insertion order), newest/oldest (`createdAt`), priority (`high>medium>low`), due-date (`dueDate` ascending with `null` due dates last). The active sort is re-applied after each mutation and on each sort change.
- **Search**: a case-insensitive `includes` match on title, combined with the active filter via composition.
- **Statistics**: derived counts (total, active, completed) and `Math.round(completed/total*100)` percentage, recomputed on every mutation; empty list yields zeros.
- **Rendering**: all list items are built with `document.createElement` and `textContent`; no `innerHTML` is used for titles. Re-render diffing is kept simple by rebuilding the visible list from the filtered/sorted view, which is performant for typical list sizes.

### QuickLinksManager

- **Defaults**: seeded to Google, YouTube, GitHub, Gmail, Notion when the key is absent.
- **CRUD**: add/edit/delete update the in-memory list and persist each time.
- **URL validation**: the URL is parsed with the `URL` constructor inside a try/catch; accepted only when `protocol` is `http:` or `https:`. Missing-protocol and `javascript:`/`data:`/`file:` URLs are rejected with an inline error message and not saved.
- **New tabs**: anchors are created with `target="_blank"` and `rel="noopener noreferrer"` and their `href` set via the `href` property (not innerHTML).

### ThemeController

- **Anti-flash init**: a tiny inline script in `<head>` reads `lifeDashboard.theme.v1` (falling back to `prefers-color-scheme` on first visit) and sets the `data-theme` attribute on `<html>` before the body renders, preventing a flash of the wrong theme.
- **Toggle**: flips the `data-theme` attribute and persists the new value.
- **CSS variables**: all colors, backgrounds, borders, and shadows are defined as CSS variables scoped under `[data-theme="light"]` and `[data-theme="dark"]`, so toggling the attribute re-themes the whole UI instantly.

## CSS and Theming Architecture

### CSS Variables

- `--color-primary`: `#635BFF` (light) / `#8B83FF` (dark) accent.
- Background, surface, text, border, shadow, and status colors are variables that swap per theme.
- Typography, spacing, and radii are shared variables independent of theme.

### Layout

- A CSS Grid container arranges the major panels (Clock/Greeting, Pomodoro, Tasks, Quick Links).
- Breakpoints:
  - `> 1024px`: multi-column grid (e.g., sidebar + main).
  - `768px-1024px`: tablet two-column or reflowed grid.
  - `< 768px`: single column, stacked panels.

### Reduced Motion

- A `@media (prefers-reduced-motion: reduce)` rule disables transitions and animations, replaced by instant state changes.

## Accessibility Design

- Semantic landmarks: `<header>`, `<main>`, `<section>` per widget, `<footer>`.
- All interactive controls are real `<button>`, `<input>`, `<select>` elements; no clickable `<div>` without a role and keyboard handler.
- ARIA labels on icon-only buttons (e.g., theme toggle, delete, edit, timer controls).
- Visible `:focus` and `:focus-visible` outlines retained in both themes.
- The timer ring carries an `aria-label`/`role` describing remaining time; live regions announce completion.
- Color choices meet WCAG AA contrast for text on surfaces in both themes.

## Key Algorithms

### Timer Drift Resistance

```
start():   targetEnd = Date.now() + durationMs; tick()
tick():    remaining = targetEnd - Date.now()
           if remaining <= 0: complete()
           else: render(remaining); schedule next tick in 1000ms (or sooner)
pause():   remainingMs = targetEnd - Date.now(); clear timer
resume():  targetEnd = Date.now() + remainingMs; tick()
```

Because `remaining` is recomputed from the absolute `targetEnd`, time spent with the tab backgrounded (where timers may be throttled) is accounted for when the tab regains focus.

### Duplicate Detection

```
normalize(title) = title.trim().toLowerCase()
isDuplicate(title) = existingTasks.some(t => normalize(t.title) === normalize(title))
```

Applied on add and on inline edit (excluding the task being edited).

### URL Validation

```
function isValidUrl(input):
    try: u = new URL(input)
    catch: return false
    return u.protocol === "http:" || u.protocol === "https:"
```

### Sorting

Comparators return a stable ordering; manual sort preserves the stored array order. For due-date, tasks with `dueDate === null` are pushed after all dated tasks.

## Rendering and DOM Safety

- User content (task titles, link titles, display name) is inserted exclusively through `textContent` and attribute assignment via the DOM API.
- Static structure may use template literals assigned to element properties only where no user data is interpolated; any user-derived value bypasses `innerHTML`.
- Event delegation is used for the task list and quick links list to avoid per-item listeners and to handle dynamically added rows.

## Error Handling

| Edge case | Handling |
|---|---|
| Empty task list | Empty-state message; stats show zeros. |
| All tasks completed | "All complete" state; percentage 100%. |
| Duplicate submission | Rejected; existing task unchanged. |
| Special characters in titles | Rendered literally via `textContent`. |
| Cancel editing | Escape restores the original title. |
| Invalid URL | Inline error; link not saved. |
| Malformed JSON in storage | Parsed value discarded; default returned. |
| Storage unavailable | In-memory state used for the session. |
| Tab inactivity during timer | `targetEnd` keeps time accurate on refocus. |
| Timer reaching zero | Stops, shows 00:00, optional notification. |
| Theme change during timer | JS timer state untouched; countdown continues. |
| Page refresh after saves | Data reloaded from versioned keys. |
| Filter switching | Underlying list preserved; view recomputed. |
| Repeated sort changes | Re-sorted each time; data intact. |
| URL without protocol | Rejected by `URL` constructor protocol check. |
| Disallowed protocols | `javascript:`/`data:`/`file:` rejected. |
| Undated task in due-date sort | Placed at the end of the sorted view. |

## Design Decisions and Trade-offs

- **Single `app.js` over ES modules**: chosen so the app runs from `file://` without a server. Internal IIFE modules preserve separation. Trade-off: a larger single file, mitigated by clear section comments.
- **Rebuild-render over diffing**: for typical list sizes, rebuilding the filtered/sorted view is simpler and fast enough, avoiding a virtual DOM dependency. Trade-off: less optimal for very large lists, out of scope here.
- **Target timestamp over interval decrement**: chosen for drift resistance and tab-inactivity correctness. Trade-off: requires re-deriving remaining time each tick, which is trivial.
- **No permission request for notifications**: respects the requirement to only notify when permission is already granted; avoids surprising prompts. Trade-off: users must grant permission elsewhere; an in-app completion indicator covers the ungranted case.
- **Default quick links seeded only on first load**: prevents re-seeding after a user clears the list. Distinguished by key presence, not by an empty array.

## Correctness Properties

This section maps key acceptance criteria to testable properties to guide implementation and verification.

### Property 1: Storage round trip

**Given:** a value `v` is saved under a versioned key through the Storage layer,
**When:** `load(key)` is called,
**Then:** the returned value is equivalent to `v`. Applies to tasks, quick links, theme, and settings.
**Validates: Requirements 25**

### Property 2: Duplicate prevention

**Given:** an existing task list,
**When:** a task is added whose normalized title equals an existing task's normalized title,
**Then:** the list length does not change and no task is added.
**Validates: Requirements 9**

### Property 3: URL validation

**Given:** a submitted quick link URL,
**When:** the URL is validated,
**Then:** only URLs with `http:` or `https:` protocols are accepted; `javascript:`, `data:`, `file:`, and protocol-less inputs are rejected.
**Validates: Requirements 21**

### Property 4: Timer accuracy across inactivity

**Given:** a running Pomodoro session using a target timestamp,
**When:** the browser tab is inactive for a period and then regains focus,
**Then:** the displayed remaining time equals `targetEnd - Date.now()` rather than a decremented counter value.
**Validates: Requirements 5**

### Property 5: Sorting stability

**Given:** a task list with dated and undated tasks,
**When:** the list is sorted by due-date,
**Then:** every task with `dueDate === null` appears after all dated tasks; manual sort preserves insertion order across repeated re-sorts.
**Validates: Requirements 15**

### Property 6: Idempotent toggling

**Given:** a task with a `completed` value,
**When:** the completion control is toggled twice,
**Then:** the `completed` value returns to its original state and all other fields are preserved.
**Validates: Requirements 11**

### Property 7: Theme continuity during timer

**Given:** a running Pomodoro session,
**When:** the theme is changed,
**Then:** `targetEnd` and `remainingMs` remain unchanged and the countdown continues.
**Validates: Requirements 24**

### Property 8: Safe rendering of special characters

**Given:** a task title containing `<`, `>`, `&`, or quotes,
**When:** the task is rendered,
**Then:** the characters appear as literal text and the task row gains no child elements.
**Validates: Requirements 29**

## Testing Strategy

The test approach combines property-based checks for logic that varies meaningfully with input with integration-style smoke tests for wiring and static behavior.

- **Property-based checks** cover variable-input logic: storage round trips, duplicate prevention, URL validation, sorting stability (especially undated tasks in due-date sort), idempotent toggling, and safe rendering of special characters. These run over generated inputs because behavior changes with the data.
- **Integration smoke tests** (1-2 representative examples each) cover behavior that does not vary with input: initial render shows default quick links, the empty task state renders, and the correct theme applies on first load with `prefers-reduced-scheme`. These validate that components are wired together rather than re-test browser or library behavior.
- **No browser/service mocking of external systems**: the Notification API is checked by example only when permission is already granted; storage-unavailable behavior is checked with a single example.
